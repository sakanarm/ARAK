# Policy ชนกัน แล้วใครชนะ?

เอกสารนี้ตอบคำถามเดียว: **เมื่อ policy หลายตัวมีผลกับตารางเดียวกันพร้อมกัน ระบบตัดสินยังไง**

เขียนสำหรับคนที่เขียน policy — data owner, policy author, ผู้ดูแลระบบ ไม่ต้องอ่านโค้ดก็เข้าใจได้
(ฝั่งเทคนิคอยู่ที่ [policy-spec.md](policy-spec.md) · การตัดสินทั้งหมดเกิดที่ `PolicyEngine` ที่เดียว
ทั้งสามโหมด enforcement ใช้ผลตัดสินชุดเดียวกัน จึงให้คำตอบตรงกันเสมอ)

---

## สรุปใน 5 บรรทัด

1. **DENY ชนะทุกอย่าง** — มี DENY ตัวเดียว match จบเลย ไม่ต้องนับ ALLOW
2. **ไม่มี policy = ไม่ได้** — เงียบคือปฏิเสธ (fail-closed)
3. **ชั้นเดียวกัน = OR** — มี ALLOW ตัวใดตัวหนึ่งผ่านก็พอ
4. **ข้ามชั้น = AND** — ต้องผ่านทุกชั้นที่มี ALLOW ตกชั้นเดียวจบ
5. **เห็นอะไรในตาราง = เข้มสุดชนะเสมอ** — ไม่มี "เอาอันล่าสุด" ไม่มีเลขลำดับความสำคัญ

---

## ตาราง Conflict — ตัวหลัก

| สถานการณ์ | ผลลัพธ์ | เหตุผล |
|---|---|---|
| **ALLOW ชน DENY** | **DENY ชนะ** ทุกกรณี | DENY คือการตัดสินใจที่มีคนตั้งใจเขียน การปล่อยให้ ALLOW ปลดมันได้ = ปลดของที่ security ตั้งไว้โดยไม่มีใครรู้ |
| **ไม่มี policy ตัวไหน match เลย** | **ปฏิเสธ** | ถ้าเงียบแปลว่าอนุญาต ตารางใหม่ที่เพิ่งเข้าระบบจะเปิดให้ทุกคนทันที |
| **ALLOW หลายตัว แขวนชั้นเดียวกัน** | **ผ่านถ้ามีตัวใดตัวหนึ่งผ่าน (OR)** | คนเดียวอยู่หลายทีม ทีมไหนให้สิทธิ์ก็ได้สิทธิ์ ไม่ต้องผ่านทุกทีม |
| **ALLOW หลายตัว แขวนคนละชั้น** | **ต้องผ่านทุกชั้น (AND)** | ชั้นบนคือกติกาองค์กร ชั้นล่างคือกติกาเจ้าของข้อมูล — เจ้าของข้อมูลปลดกติกาองค์กรเองไม่ได้ |
| **ชั้นที่ไม่มี ALLOW เลย** | **ข้ามไป ไม่นับเป็นด่าน** | ไม่งั้นแค่ไม่ได้เขียน policy ระดับ SERVICE ทุกคนจะเข้าไม่ได้ทั้งระบบ |
| **Row filter หลายตัว** | **AND กันทั้งหมด** — เห็นเฉพาะแถวที่ผ่านครบทุกเงื่อนไข | filter คือการจำกัด ยิ่งมีหลายคนจำกัดยิ่งต้องแคบลง ไม่ใช่กว้างขึ้น |
| **Mask หลายตัวบน column เดียว** | **ตัวเข้มที่สุดชนะ** (ดูตารางความเข้มข้างล่าง) | ถ้าเลือกตัวหลวม = คนที่ตั้งใจปิดข้อมูลถูกปลดโดยไม่รู้ตัว |
| **Mask ความเข้มเท่ากัน** | **ตัวที่เจอก่อนอยู่** | เพื่อให้ผลลัพธ์**ไม่ขึ้นกับลำดับ** — รันกี่ครั้ง ผ่านโหมดไหน ก็ได้ผลเดิม |
| **Mask ชน Hide บน column เดียว** | **Hide ชนะ** — column หายไปเลย ไม่โผล่ใน schema ด้วยซ้ำ | ซ่อนแล้วไม่เหลืออะไรให้ mask |
| **เงื่อนไขตัดสินไม่ได้** (attribute ของ user หาย / เขียน expression ผิด) | **นับเป็นลบกับคนถาม** | ข้อมูลไม่ครบ = ไม่ให้ผ่าน ไม่ใช่ให้ผ่านไปก่อน |
| **Row filter อ้าง attribute ที่ user ไม่มี** | **กลายเป็น "ไม่เห็นแถวไหนเลย"** ไม่ใช่ถูกตัดทิ้ง | ถ้าตัด filter ทิ้ง = เห็นทุกแถว ซึ่งตรงข้ามกับที่ policy ตั้งใจ |
| **ชั้นล่างอยากผ่อนชั้นบน** | **ทำไม่ได้** เว้นแต่ policy ชั้นบนเปิด `allowLocalOverride` ไว้เอง | และทุกครั้งที่ใช้จะถูกบันทึกไว้ว่าใครผ่อน ผ่อนอะไร |

## ลำดับความเข้มของ Mask

เมื่อหลาย policy สั่ง mask column เดียวกันคนละแบบ ระบบเลือกตัวที่อยู่**สูงกว่า**ในตารางนี้

| ลำดับ | Function | เห็นอะไรเหลือ |
|---|---|---|
| 7 (เข้มสุด) | `NULLIFY` | ว่างเปล่า |
| 6 | `CONSTANT` | ข้อความตายตัว เช่น `***REDACTED***` |
| 5 | `HASH` | ค่าที่อ่านไม่ออก แต่ join ได้ (ค่าเดิมให้ผลเดิมเสมอ) |
| 4 | `REGEX_REPLACE` | เหลือบางส่วนตามที่กำหนด เช่น `***@mfec.co.th` |
| 3 | `PARTIAL` | เหลือท้าย n ตัว เช่น `*******1234` |
| 2 | `ROUNDING` | ค่าหยาบขึ้น เช่น วันเกิด → ปีเกิด, เงินเดือน → ช่วง |
| 1 | `CONDITIONAL` | mask เฉพาะบางแถว (ดู ⚠️ ข้อควรรู้ ข้อ 2) |
| 0 (หลวมสุด) | ไม่ mask | ค่าจริง |

> **`HASH` เข้มกว่า `PARTIAL`** เพราะไม่เหลือส่วนไหนของค่าเดิมให้อ่านได้เลย ถึงแม้จะยัง join ได้อยู่
> **`ROUNDING` อยู่ล่างสุด** เพราะยังบอกช่วงของค่าจริงอยู่

## "ชั้น" คืออะไร

ตารางหนึ่งตัวไม่ได้ลอยเดี่ยว มันอยู่ในลำดับชั้นนี้ และ policy แขวนได้ทุกชั้น

```
ORG                        ← ทั้งองค์กร
 └ DOMAIN                  ← Finance → Finance.Risk → Finance.Risk.Credit
    └ SERVICE              ← prod-mssql
       └ DATABASE          ← SalesDB
          └ SCHEMA         ← dbo
             └ TABLE       ← customer
                └ COLUMN   ← citizen_id
```

ตอนสร้าง policy คุณเลือก `scopeLevel` ว่าจะแขวนชั้นไหน — แขวน `ORG` คือคุมทั้งองค์กร
แขวน `TABLE` คือคุมตารางเดียว **ชั้นที่ลึกกว่าอยู่ล่างกว่าเสมอ และผ่อนชั้นบนไม่ได้**

> `DOMAIN` ซ้อนกันเองได้ — policy บน `Finance` กับ policy บน `Finance.Risk.Credit`
> ถือเป็นคนละชั้น โดยตัวที่ลึกกว่าอยู่ล่างกว่า

---

## ตัวอย่างที่ 1 — ตกชั้นเดียวก็จบ (AND ข้ามชั้น)

`analyst_a` · ทีม Finance · clearance L1 · ขอดู `SalesDB.dbo.customer`

| Policy | แขวนที่ | เงื่อนไข | ผ่าน? |
|---|---|---|---|
| A | ORG | ALLOW คนที่ `clearance >= L1` | ✅ |
| B | DOMAIN `Finance` | ALLOW `team = Finance` | ✅ |
| C | TABLE `customer` | ALLOW `team = Risk` | ❌ |

```
ORG      ✅
DOMAIN   ✅   ── AND ──→  ❌ ปฏิเสธ
TABLE    ❌
```

**ผล: ปฏิเสธ** — ผ่าน 2 ชั้นแรกแล้วแต่ตกชั้น TABLE
เจ้าของตารางตั้งใจให้เฉพาะทีม Risk เห็น การที่องค์กรอนุญาตกว้างๆ ไม่ได้ปลดข้อนั้น

---

## ตัวอย่างที่ 2 — ชั้นเดียวกันขอแค่ตัวเดียว (OR ในชั้น)

เพิ่ม policy D แขวนที่ **TABLE `customer` ชั้นเดียวกับ C**

| Policy | แขวนที่ | เงื่อนไข | ผ่าน? |
|---|---|---|---|
| C | TABLE `customer` | ALLOW `team = Risk` | ❌ |
| D | TABLE `customer` | ALLOW `team = Finance` | ✅ |

```
ชั้น TABLE:  C ❌  OR  D ✅  =  ✅ ผ่าน
```

```
ORG      ✅
DOMAIN   ✅   ── AND ──→  ✅ อนุญาต
TABLE    ✅
```

**ผล: อนุญาต** — C ไม่ผ่านไม่เป็นไร เพราะ D อยู่ชั้นเดียวกันและผ่านแล้ว

> นี่คือคำตอบของ *"อยู่หลาย group แล้วแต่ละ group มี policy — union กันใช่ไหม"*
> **ใช่ ถ้า policy พวกนั้นแขวนชั้นเดียวกัน** แต่ถ้าแขวนคนละชั้น มันกลายเป็นด่านที่ต้องผ่านครบแทน

---

## ตัวอย่างที่ 3 — DENY ตัวเดียวจบ

`analyst_b` · ทีม Finance · clearance L2 · country = SG

| Policy | แขวนที่ | เงื่อนไข | ผล |
|---|---|---|---|
| A | ORG | ALLOW `clearance >= L1` | ✅ |
| B | DOMAIN `Finance` | ALLOW `team = Finance` | ✅ |
| D | TABLE `customer` | ALLOW `team = Finance` | ✅ |
| **E** | **ORG** | **DENY ถ้า `user.country != asset.prop('dataResidency')`** | **🚫 match** |

**ผล: ปฏิเสธ** — ผ่านทุกชั้น ALLOW ครบหมด แต่ไม่มีความหมาย
`customer` มี `dataResidency = TH` ส่วน `analyst_b` อยู่ SG → DENY match → **จบทันที ไม่ต้องนับ ALLOW**

---

## ตัวอย่างที่ 4 — Row filter สะสมกัน ยิ่งเยอะยิ่งเห็นน้อย

`analyst_a` · branch = `BKK-01` · ผ่าน subscription มาแล้ว มี data policy 3 ตัวมีผลพร้อมกัน

| Policy | แขวนที่ | Row filter |
|---|---|---|
| F | SCHEMA `dbo` | `branch_code = user.branch` |
| G | TABLE `customer` | `status != 'DELETED'` |
| H | DOMAIN `Finance` | `created_at >= '2024-01-01'` |

SQL ที่ระบบสร้างให้จริง:

```sql
WHERE branch_code = 'BKK-01'
  AND status != 'DELETED'
  AND created_at >= '2024-01-01'
```

**ผล: เห็นเฉพาะแถวที่ผ่านครบทั้ง 3 เงื่อนไข**

> ⚠️ **ไม่มีทางที่ policy ตัวที่ 4 จะมา "ปลด" filter ของ 3 ตัวแรกได้**
> การเพิ่ม data policy ทำให้เห็นน้อยลงเสมอ ไม่เคยทำให้เห็นมากขึ้น

## ตัวอย่างที่ 5 — Mask ชนกันบน column เดียว

`analyst_a` ขอดู column `email` ของ `customer` มี 3 policy สั่ง mask คนละแบบ

| Policy | แขวนที่ | สั่ง | ความเข้ม |
|---|---|---|---|
| I | ORG | `REGEX_REPLACE` → `***@mfec.co.th` | 4 |
| J | SCHEMA `dbo` | `PARTIAL` เหลือท้าย 4 ตัว | 3 |
| K | TABLE `customer` | `HASH` | **5** ← ชนะ |

**ผล: เห็นเป็น `HASH`** — เข้มที่สุดในสามตัว

> **สังเกตว่า policy ชั้น ORG ไม่ได้ชนะเพราะอยู่ชั้นบนสุด** — ชั้นไม่เกี่ยวกับการเลือก mask เลย
> ชั้นมีผลกับ "เข้าได้ไหม" เท่านั้น ส่วน "เห็นเป็นอะไร" ตัดสินด้วยความเข้มล้วนๆ

### เพิ่ม Hide เข้าไปอีกตัว

| Policy | แขวนที่ | สั่ง |
|---|---|---|
| I, J, K | (ตามข้างบน) | mask แบบต่างๆ |
| L | COLUMN `customer.email` | **HIDE** |

**ผล: column `email` หายไปเลย** ไม่โผล่ใน `SELECT *` ไม่โผล่ในรายการ column ด้วยซ้ำ
mask ทั้งสามตัวไม่มีความหมายเพราะไม่มีค่าเหลือให้แปลง

---

## ตัวอย่างที่ 6 — เคสที่คนพลาดบ่อยที่สุด

เจ้าของตาราง `customer` อยากให้ทีม Marketing ดู `citizen_id` แบบไม่ mask
จึงเขียน policy แขวนที่ TABLE: *ALLOW `team = Marketing` เห็น `citizen_id` เต็ม*

**ผลจริง: ยังถูก mask อยู่**

เพราะมี policy ระดับ ORG อยู่ว่า *mask ทุก column ที่ `classifications contains 'PII'`
ยกเว้นคนที่ `clearance >= L2`* และ `citizen_id` ติด tag `PII.Sensitive`

policy ที่เจ้าของเขียน**ไม่ได้ผิด** แต่**ไม่พอ** — ชั้นล่างเพิ่มความเข้มได้ แต่ผ่อนชั้นบนไม่ได้

**ทางออกที่ถูกต้อง** เลือกอย่างใดอย่างหนึ่ง:
1. ให้ทีม Marketing ได้ `clearance L2` (แก้ที่ attribute ของคน ไม่ใช่ที่ policy)
2. ขอให้เจ้าของ policy ระดับ ORG เปิด `allowLocalOverride: true` ให้ — ซึ่งจะถูกบันทึกทุกครั้งที่มีคนใช้
3. ถอด tag `PII.Sensitive` ออกจาก column (ควรคิดให้ดีก่อน — มันจะกระทบทุก policy ที่อ้าง tag นี้)

> หน้า Policy Builder ต้องเตือนเรื่องนี้**ตอนกำลังเขียน** ไม่ใช่ปล่อยให้ไปเจอตอน production

---

## ⚠️ ข้อควรรู้ 3 ข้อ

**1. "อยู่หลาย group" ไม่ได้แปลว่าได้สิทธิ์มากขึ้นเสมอไป**
อยู่ 5 group ที่ allow หมด → ผ่าน subscription ง่ายขึ้นจริง (OR ในชั้น)
แต่ data policy ของทั้ง 5 group จะถูกเอามา **AND กันหมด** และ mask จะเอาตัวเข้มที่สุดในบรรดานั้น
**ยิ่งอยู่หลาย group ยิ่งมีโอกาสเจอ filter และ mask เยอะขึ้น**

**2. `CONDITIONAL` อยู่ลำดับ 1 ซึ่งต่ำกว่าทุก function จริง**
ถ้าคุณเขียน *"mask `salary` เฉพาะแถวที่ไม่ใช่แผนกตัวเอง"* (`CONDITIONAL`)
แล้วมีอีก policy สั่ง `ROUNDING` บน column เดียวกัน → **`ROUNDING` ชนะ และเงื่อนไขของคุณหายไปทั้งก้อน**
กลายเป็นปัดเศษทุกแถวแทน ซึ่งบางเคสหลวมกว่าที่คุณตั้งใจ
**ถ้าต้องการ cell mask ให้แน่ใจว่าไม่มี policy อื่น mask column เดียวกันอยู่**

**3. ผลลัพธ์ไม่ขึ้นกับลำดับ — ตั้งใจให้เป็นแบบนั้น**
ไม่มี "เอาอันล่าสุด" ไม่มีเลข priority ให้ตั้ง จะสร้าง policy เรียงยังไง แก้ตอนไหน
ผลตัดสินก็เหมือนเดิม และทั้งสามโหมด enforcement (source config / secure view / proxy)
ต้องให้ผลตรงกันทุก byte ซึ่งเป็นไปได้ก็เพราะกติกาไม่ขึ้นกับลำดับนี่แหละ

## ทำไมไม่ใช้ "เอาอันล่าสุด" หรือ "ตั้งเลขลำดับ"

| แบบ | ปัญหา |
|---|---|
| **เอาอันล่าสุด** | คนแก้ policy ตอนบ่ายปลด policy ที่ security เขียนไว้ตอนเช้าโดยไม่รู้ตัว และตอบคำถาม *"ทำไมเมื่อวานเห็น วันนี้ไม่เห็น"* ไม่ได้ |
| **ตั้งเลขลำดับเอง** | กลายเป็นสงครามเลข (ใครตั้ง 999) และการตรวจสอบต้องไล่อ่าน policy ทั้งองค์กรถึงจะรู้ว่าอะไรชนะ |
| **เข้มสุดชนะ (ที่ใช้อยู่)** | ถ้าตั้งผิด ผลคือ**เห็นน้อยกว่าที่ควร** → มีคนมาบ่น แล้วแก้ได้ ไม่ใช่ข้อมูลหลุดเงียบๆ โดยไม่มีใครรู้ |

หลักคือ **ความผิดพลาดต้องเอนไปทางปลอดภัย** ระบบที่ตั้งผิดแล้วข้อมูลหลุดเงียบๆ คือระบบที่ไม่มีใครกล้าใช้

---

## อยากรู้ว่า "ทำไมถึงโดน"

ทุกการตัดสินจะมีรายการเหตุผลติดมาด้วยเสมอ — ระบุว่าข้อจำกัดแต่ละอย่าง
**มาจาก policy ตัวไหน แขวนชั้นไหน เงื่อนไขข้อไหน**

ใช้หน้า **Simulator / View as user** ดูล่วงหน้าได้ว่าคนคนหนึ่งจะเห็นตารางนี้เป็นอย่างไร
ก่อนจะ publish policy จริง
